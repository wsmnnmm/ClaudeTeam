# C5｜模型岗位分层与限流治理草案

更新时间：2026-05-22

> 状态：草案。本文只定义原则和执行边界，**不直接修改任何模型配置、不重启团队、不切 provider、不部署**。

## 0. 背景

当前四队已经进入 C1-C4：

- C1：只读巡视
- C2：本地 30 分钟自动刷新驾驶舱
- C3：老板简报与红色故障提醒
- C4：必要时最小唤醒 manager

新暴露的问题不是“模型总额度不够”，而是 24 小时 AI 团队从单人 Codex 模式变成多人并发后，容易触发：

- provider / 中转 API `429 Too Many Requests`
- manager 卡住但 tmux/router/watchdog 仍显示在线
- 多个 worker 同时抢高阶模型通道
- 黄色问题被过度唤醒，导致短时间并发升高

因此 C5 的目标不是“把 worker 降级”，也不是“所有人都上最高模型”，而是建立一套：

> **主管快稳、员工强深、验收高智商、巡视脚本化、429 先冷却排队而不是盲改模型。**

## 2. C5 总原则

### 2.1 主管不是最强执行线程，而是前台调度台

manager 的首要指标：

```text
快、稳、短反馈、会拆、会派、会验收、会向老板翻译
```

manager 不应该长时间占用最高智商模型做深度实现。它要保证：

1. 老板消息先被接住。
2. 1-3 分钟内给当前事实 / 卡点 / 下一步。
3. 长任务交给专岗 worker。
4. worker 输出必须被压缩、验收、翻译成老板语言。
5. 遇到登录、429、权限、生产动作，及时报 blocker。

### 2.2 worker 才是深度产出的主力

worker 的首要指标：

```text
能力上限、复杂推理、代码质量、研究深度、可验收证据
```

不能为了省 token 或降低并发，把关键 worker 统一降级成弱模型。否则会带来：

- 返工增加
- 幻觉增加
- 代码质量下降
- manager 验收负担变大
- 老板看到更多“忙但不交付”

### 2.3 reviewer / 质量闸门应使用高智商模型

复杂任务必须有验收者。reviewer 不是装饰岗位，它决定：

- worker 交付是否真实
- 截图/日志/代码/接口证据是否完整
- 是否还有隐藏风险
- 是否可以对老板说“阶段完成”

因此 reviewer / 审计型 worker 应优先使用高能力模型。

### 2.4 monitor / 巡视 / dashboard 尽量脚本化

C1-C3 已经证明：很多巡视和汇报不需要模型。

脚本适合做：

- health 读取
- task list 读取
- heartbeat 判断
- 429 字符串识别
- active task 计数
- 生成固定格式老板简报

模型不应该浪费在可确定的巡检逻辑上。

## 3. 推荐岗位模型分层

| 岗位 | 核心能力 | 模型策略 | 说明 |
|---|---|---|---|
| manager | 快速响应、拆派、收口、老板翻译 | 中高智商 + 高稳定 + 低延迟 | 不一定最强，但不能慢、不能卡 |
| builder / frontend / engineer | 代码实现、复杂修复 | 高能力模型 | 质量优先，允许较慢，但必须有证据 |
| researcher / scout | 资料检索、代码侦察、根因假设 | 高上下文/高推理模型 | 输出必须区分事实/假设/待验证 |
| reviewer / audit | 质量闸门、反证、验收 | 高智商模型 | 防止 worker 半成品被当最终结果 |
| visual / design | UI 还原、截图理解、生图 | 多模态/视觉强模型 | 图片识别和生图链路分开治理 |
| memory / secretary | 台账、摘要、项目卡片 | 稳定低成本模型 | 不承担关键判断 |
| monitor / cockpit | 巡视、计数、告警 | 脚本 | 尽量不用模型 |

## 4. 429 限流解释与治理原则

### 4.1 429 不等于总额度用完

`429 Too Many Requests` 更常见含义是：

- 每分钟请求数超过限制
- 每分钟 token 超过限制
- 并发 streaming 请求过多
- 某个模型池当前容量不足
- 自定义 provider / 中转 API 自己限速
- 多团队共用同一路由造成互相影响

因此当老板说“我模型还有额度”时，正确解释是：

> 总额度还在，但当前并发/速率/上游路线被限流。

### 4.2 429 时优先排队和冷却，不默认降 worker 模型

C5 默认顺序：

1. 记录触发团队、agent、model、provider/base_url、时间。
2. 判断是否只是短时 429。
3. 对同一团队进入冷却，不连续唤醒。
4. 保留 worker 高能力模型，不做全员降级。
5. 如果 manager 卡住，优先保障 manager 快速回执通道。
6. 多次连续 429 后，才进入人工确认的 provider/模型切换方案。

### 4.3 高能力 worker 需要并发闸门，不需要默认降级

原则：

```text
强模型可以用，但不能无限并发抢。
```

推荐方向：

- 同时深度执行的高能力 worker 数量有限制。
- manager 快速响应通道保留最小容量。
- reviewer 按事件触发，不常驻空转。
- 黄色观察不频繁唤醒，避免制造并发尖峰。

## 5. C5 分阶段实施建议

### C5.0 草案阶段（当前）

只做文档和讨论。

允许：

- 读取现有配置和 SOP
- 归并原则
- 标出冲突点
- 提出可选方案

禁止：

- 改模型
- 改 provider
- 重启团队
- 杀 Codex 进程
- 修改任务状态

### C5.1 观测阶段

目标：知道谁在用什么、什么时候限流。

建议新增只读报告：

```text
runtime-health/model-usage-snapshot.md
runtime-health/provider-rate-limit-events.md
```

采集内容：

- 当前 Codex 进程数量
- 按 model 聚合数量
- 每队 manager/worker 当前配置模型
- 最近 429 日志时间、thread、model、provider/base_url
- 是否由 C4 唤醒后集中出现

仍然禁止自动改模型。

### C5.2 并发闸门草案

先只定义规则，不强制执行：

- 高能力 worker 同时深度运行建议上限
- manager 快速响应保留通道
- reviewer 只在交付验收时触发
- 黄色观察仅进报告，不默认唤醒
- 红色故障才触发 C4 wakeup

### C5.3 软执行

在 manager wakeup 文案中加入调度建议：

- 如果 429，先冷却，不要连续重试。
- 只推进一个最关键任务。
- 不要同时唤醒多个 worker 抢同一路由。
- 如果 worker 深度任务已在跑，manager 只做老板回执，不重复派活。

### C5.4 恢复策略（需再次确认）

只有连续 72 小时观测后，再考虑：

- manager 卡死是否自动重启 pane
- router/watchdog 掉线是否自动重启
- provider 死亡是否自动切备用 preset
- 是否自动暂停部分 worker

这一阶段必须单独确认，不随 C5 草案默认启用。

## 8. 一句话原则

C5 不应该把团队做成“便宜模型大锅饭”，也不应该让所有岗位无限抢最高模型。

正确方向是：

> **主管快稳接住老板，worker 高智商做难活，reviewer 高智商把关，monitor 脚本化巡检，429 先冷却排队，恢复动作必须有边界。**
