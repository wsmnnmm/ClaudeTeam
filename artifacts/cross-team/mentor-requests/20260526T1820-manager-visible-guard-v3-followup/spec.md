# ClaudeTeam manager 自然语言进度汇报机制 V3 追问 SPEC

## 背景

刘小排上一轮给 V2 方案 8 分。方向对，但缺口是“状态卡”还像技术降级日志，不像老板真正愿意看的进度汇报。

本轮把方案从“系统状态卡”升级为“自然语言进度汇报”。目标不是让系统勉强发一条降级消息，而是让老板在追问后 2 分钟内看到一条像同事同步进展一样自然、能降低焦虑的回复。

## V3 方案

### 产品定义

名称：自然语言进度汇报。

使命：老板追问进展后，先回答“谁在做、做到了哪、卡在哪、什么时候下一次回”，而不是等待完整结论。

示例模板：

> 进度更新：正在检查小红书“交友”搜索结果。初步判断：内容偏婚恋，和深圈活动目标人群有偏差，所以已暂停互动。正在整理截图和风险说明，预计 5 分钟后发完整报告。负责人：manager。

### 基座代码改动

1. 抽出一个可复用的“进度汇报生成/校验”逻辑。
2. 主动触发：
   - manager 收到老板“进展如何/现在怎么样/卡住了吗/还没好吗”等追问类消息；
   - manager 根据任务类型或规则判断完整回复预计超过 2 分钟；
   - 先发一条自然语言进度汇报，再继续组织正式结论。
3. 被动降级：
   - `say_blocked` 原因属于缺图、缺附件、缺预览 URL、图片发送失败、可见证据格式不足时；
   - 调用同一个进度汇报逻辑；
   - 说明“证据准备/发送遇到技术问题，正在补齐”，并给下次更新时间；
   - 原完整消息写入 manager inbox，作为正式报告待补。
4. 进度汇报可以绕过图片/预览类门禁，但必须通过轻量校验：
   - 不能宣称“已完成/已通过/已验收/最终结论”；
   - 必须包含当前动作、当前判断或卡点、下一次更新时间/负责人；
   - 语言要面向老板，不能是 `[系统]` 日志口吻。

### 预估超过 2 分钟的规则

先不用复杂模型，使用保守规则：

1. 涉及截图、浏览器、图片压缩、附件上传、预览 URL、视觉/UI 验收、外部平台页面验证，默认预计超过 2 分钟。
2. 老板追问同一任务且当前已有 worker 在执行、manager 正在验收、或刚出现 `say_blocked/say_failed`，默认预计超过 2 分钟。
3. manager 可以主动判断“马上能一句话给结论”，则不用发进度汇报，直接给结论。

### 团队 SOP 改动

1. 老板追问时，manager 第一优先级是“人话进度”，不是完整报告。
2. 完整报告需要图片/链接/截图/长分析时，先发进度汇报，再由 worker/runner 补证据。
3. 进度汇报不是验收结论；它只负责降低等待焦虑和暴露真实卡点。

### 不做

1. 不做 watchdog 自动 recycle manager。
2. 不做复杂“正式收口闸门”。
3. 不把所有 `say_blocked` 当任务失败，只处理可见证据/附件/预览类阻塞。

### 验收用例

1. 老板问“进展如何”，当前任务涉及截图/浏览器/视觉证据。
   - 期望：2 分钟内出现自然语言进度汇报。
2. `say_blocked` 因缺图或缺 preview URL 拦截正式报告。
   - 期望：自然语言进度汇报发出，原正式报告进入 manager inbox。
3. 进度汇报试图说“已完成/已验收/通过”。
   - 期望：被轻量校验拒绝。
4. 图片发送失败。
   - 期望：仍可发纯文本进度汇报：“截图已有，发送遇到技术问题，正在补可达图/压缩图，X 分钟后回。”

### 成功指标

老板在任何团队群追问进展后，95% 情况下 2 分钟内收到自然语言进度汇报或明确结论。汇报让老板知道：谁在做、做到哪、卡在哪、下一次什么时候有信儿。
