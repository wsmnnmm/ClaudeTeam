# ClaudeTeam manager 可见状态卡降级机制 V2 追问 SPEC

## 背景

刘小排上一轮给当前草案 6 分。核心判断是：我们把“老板问进展”误当成“必须一次性给正式结论”的任务，导致图片、预览、长回复门禁把本该快速发出的状态卡拦住了。

本轮不再坚持原草案里的复杂 watchdog recycle、正式收口闸门、强制二次熔断。我们把方案收敛到刘小排给出的 10 分方向：先让老板 1-2 分钟内看到真实状态，再让 manager 后补正式结论。

## V2 方案

### 基座代码改动

1. 在 `claudeteam say` 的可见消息门禁被 `say_blocked` 拦截时，如果拦截原因属于图片、附件、预览链接或可见证据格式不足，生成一条纯文本“状态卡降级回复”。
2. 状态卡模板固定：
   - `[系统] 当前任务：<任务简述>`
   - `状态：<已知事实/正在处理/当前卡点>`
   - `预计下次更新：<X 分钟后或负责人>`
3. 状态卡可以绕过图片/预览类门禁，但仍必须满足：
   - 有 `[系统]` 前缀；
   - 不能宣称“完成/通过/已验收”；
   - 必须说明下一步或下次更新时间；
   - 原被拦截消息继续写入 manager inbox，作为“正式结论待补”任务。
4. `say_blocked` 不升级成复杂故障系统，不直接等同 `say_failed`；它只负责暴露“格式/证据未达标”，并触发状态卡降级与正式回复待办。

### 团队 SOP 改动

1. 老板在群里问“进展如何/现在怎么样/卡住了吗”等非正式追问时，第一优先级是状态，不是结论。
2. manager 判断完整回复需要超过 2 分钟时，必须先发状态卡，再继续验图、压缩图、组织正式报告。
3. 长截图、浏览器、压缩、上传、预览 URL 仍交给 worker 或 runner；manager 只负责判断当前状态、发状态卡、验收正式结论。

### 不做

1. 暂不让 watchdog 自动 recycle manager，避免误杀正常长思考。
2. 暂不做复杂“老板消息正式收口闸门”；第一条状态卡就是“未失联”证明，正式结论后补。
3. 暂不把所有 `say_blocked` 都当作任务失败；只有图片/预览/证据格式不足触发状态卡降级。

### 验收用例

1. 模拟老板问“进展如何”，manager 正在处理需要图片的任务，完整报告预计超过 2 分钟。
   - 期望：2 分钟内群里出现 `[系统]` 状态卡。
2. 模拟 `say_blocked` 原因是缺图片或缺 preview URL。
   - 期望：原消息不丢，写入 manager inbox；系统状态卡成功发出。
3. 模拟状态卡文本试图宣称“已完成/已通过”。
   - 期望：状态卡被拒绝，必须改为“当前状态/下一步”。
4. 模拟图片发送失败。
   - 期望：可发纯文本 blocker/status，而不是卡死在图片门禁。

### 成功指标

核心指标：老板发出追问后，95% 情况下 2 分钟内看到第一条有效状态卡或结论。
